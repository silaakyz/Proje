# Live Event OS — Architecture (V0.1 core)

> Plan, organise, run, measure, analyse and improve events on one platform, with AI at every step.

Status and evidence: see §5 Verification. Every claim there names the command that proves it and
whether it ran against real components or mocks.

## 0. Product model in one diagram

```
                    ┌────────────── AI Orchestrator ──────────────┐
 organizer prompt → │ Stage 1: core profile (streamed, confirmed) │
                    │ Stage 2: sections in parallel               │
                    │   registration · tasks · budget & risks     │
                    │   KPIs → data requirements → surveys        │
                    └──────────────┬──────────────────────────────┘
                                   │ every output is a PROPOSAL, never a write
                                   ▼
                     public.proposals  (cards in the workspace)
                                   │ organizer applies (may untick items)
                                   ▼
                     server/planning/apply-proposal-drizzle.ts  (one transaction, one code path)
                                   ▼
                     events (ai_config) · tasks · event_kpis · surveys · survey_questions
```

Sections `registration` (ticket types, form fields) and `budget_risks` are generated by no route yet:
they have no tables in the MVP and are reported as `unsupported`.

The Copilot (V0.2+) uses the same pipe. Read tools query the services under the caller's role. Write tools emit proposals (`task_patch` already exists) that go through the same `applyProposal`.

### Three independent axes

| Axis | Values | Source | Used for |
|---|---|---|---|
| **Event format** (`events.format`) | CONFERENCE, SYMPOSIUM, CONGRESS, FESTIVAL, TRADE_FAIR, B2B_MATCHMAKING, … | LLM, from the description | default modules, metric applicability |
| **Delivery mode** (`events.delivery_mode`) | IN_PERSON, HYBRID, VIRTUAL | LLM | hard module incompatibilities (only these) |
| **Organizer type** (`organizations.organizer_type`, optional `events.client_organizer_type`) | MUNICIPALITY, PUBLIC_INSTITUTION, UNIVERSITY, COMPANY, EVENT_AGENCY, NONPROFIT, OTHER | the organization record — never the LLM; a client only when the organizer says so | recommendations, report templates |

"Corporate event" and "municipal event" are not formats. An agency running a municipality's festival is
`organizer_type = EVENT_AGENCY`, `client_organizer_type = MUNICIPALITY`, effective type MUNICIPALITY.

### General platform, type-specific modules

- **One core for every event type.** Planning, tasks, stakeholders, registration, measurement and reporting are shared.
- **Modules on top.** `src/lib/modules/registry.ts` defines modules such as `sessions`, `speakers`, `stages`, `booths`, `matchmaking`, `sponsorship`, `site_operations`, `community_impact`, `economic_impact` and `social_media`.
- **AI configures modules; it never generates code.** Each format has deterministic default modules. Selection uses **compatibility rules, not an allow-list**: the AI or the organizer may add any module to any format (a stage at a conference, talks at a festival) — the AI must give a reason. Dependencies are added automatically (`speakers` → `sessions`). The only blocks are genuine conflicts (`site_operations`, `economic_impact` for VIRTUAL events).
- **Modules shape the plan from V0.1.** A module contributes workstreams (task columns), metrics it unlocks, stakeholder kinds and survey audiences. A festival and a congress therefore get different Blueprints today. Each module's own screens and tables ship in its `availableIn` release.
- **Recommendations come from format and organizer type** (`recommendedFor`) and are only suggestions.

## 2. Database

Plain PostgreSQL 15+ with pgvector (locally: `docker-compose.yml`). The application schema (`public`) is
defined in `src/db/schema.ts` and migrated by the committed files in `drizzle/` (0000–0008; drizzle-orm's
migrator via `npm run drizzle:migrate`). Hand-written parts of a migration are listed in its header.
Before the migrations, `scripts/db/bootstrap.sql` (idempotent) creates the platform prerequisites: pgvector,
the RLS roles (`anon`, `authenticated`, `service_role`), `auth.users` / `auth.sessions` / `auth.uid()` and
`app_private.rate_limits`.

Sign-in is the application's own (`src/server/auth/session.ts`): email + scrypt password hash in `auth.users`,
a random session token in an httpOnly cookie (or Bearer header) whose SHA-256 is stored in `auth.sessions`.
`getUserDb()` resolves the session and runs queries under RLS as `authenticated` with `auth.uid()` set.
Rate limits (sign-in, sign-up, public survey link) are counters in `app_private.rate_limits`.

KPIs: `src/lib/kpi/catalog.ts` transcribes the organization's KPI reference ("Etkinlik Etki Analizi — KPI ve Formül
Referansı (Kaynaklı)", 156 metrics with K/S/T evidence and sources); `src/lib/kpi/engine.ts` computes the ones the
platform has data for (pure, versioned); `src/server/analytics/kpi-service.ts` feeds it from the database on read.

Budget: `budget_items` (0012, server-only, owner/admin) holds planned and actual income and costs per event
(`src/server/finance/budget-service.ts`); the KPI engine computes the finance metrics from the actual amounts, and
cost lines flagged "local supplier" + "funded from outside the region" give the organizer side of the net injection.

External data (0013): `src/lib/connectors/providers.ts` defines the sources (per-event config, server env keys);
`src/server/connectors/*` are pure connectors (Open-Meteo, Brevo, GA4 with a service-account JWT, Meta Graph, YouTube,
GDELT + Google News) that return observations; `data-sources-service.ts` stores them (`data_observations`,
`media_mentions`), takes sponsor / lead CSVs, and claims due sources for automatic pulls (`scheduler.ts`, started from
`src/instrumentation.ts`). `src/lib/kpi/external.ts` turns all of it into metrics.

Own data (0014): `src/server/datasets/xlsx.ts` reads .xlsx (ZIP + XML, size / zip-bomb limits, dates from styles,
aggregate formulas and hidden sheets skipped); `src/lib/datasets/table.ts` finds the header, types the columns and
drops personal-data columns before anything is stored or sent to a model; `src/lib/datasets/measures.ts` is the
vocabulary of measures a column can mean (each feeds catalog metrics) and the header rules. The model only sees column
names and statistics to suggest meanings; a person confirms; `src/lib/kpi/datasets.ts` computes the metrics from
confirmed tables (`event_datasets`), and the interpretation is written from those computed numbers only.

Single survey link (0015, 0016): `event_survey_links` holds one token per event plus the editable first question and its
options (each opens one or more audiences' surveys, `src/lib/surveys/roles.ts`). `survey-service.ts` builds the public
form from the OPEN surveys, asks a shared question once and stores one response per opened survey in one transaction,
through the same validation as the per-survey link.

Production (docs/canliya-alma.md): `Dockerfile` (targets `app` = Next.js standalone server as an unprivileged user,
`tools` = migrations / seed / connector pulls), `docker-compose.prod.yml` (PostgreSQL 16 + pgvector, one-shot
`migrate`, app, Caddy for HTTPS, nightly `pg_dump`). The app connects as the least-privilege role created by
`scripts/db/app-role.mjs` (no DDL, BYPASSRLS for the server-side connection, member of `authenticated` for withRls);
`/api/health` is the container and proxy probe.

Input-output: `src/lib/io/data/tuik-2023.json` is generated from TÜİK's 2023 supply-use / input-output files by
`scripts/io/import-tuik-2023.py` (A64 domestic use matrix, output, GVA, compensation, household valuation column);
`src/lib/io/engine.ts` computes A, L = (I − A)⁻¹ (spectral-radius check), FLQ and the purchasers' → basic bridge;
`src/lib/io/spend-mapping.ts` maps survey spend categories to A64 products. `src/server/analytics/io-service.ts`
stores the result as an ordinary multiplier set (Type I, no employment coefficient).

```
organizations ── users (auth.users.id, one organization, role owner | admin | staff)
events (status, dates, ai_config = approved Blueprint profile)
  ├─ modules_registry
  ├─ attendees (ticket-type label, QR uuid, check-in state; no personal data)
  ├─ ai_generations (audit of every LLM call) ── proposals (human-in-the-loop cards)
  ├─ tasks · event_kpis
  ├─ surveys (version, status, public link token) ── survey_questions
  │     └─ survey_responses (anonymous; normalised visitor profile) ── survey_response_spend
  ├─ event_impact_inputs (price year, sourced deadweight/displacement/leakage, multiplier set)
  └─ impact_calculation_runs (immutable; requested/achieved level, checks, inputs, figures)
multiplier_sets ── multipliers (organization-entered, cited; per spend category)
event_analytics_vectors (pgvector, HNSW)
```

### Key rules

- **Tenant isolation.** Every tenant table carries `organization_id`; children reference their parent
  through composite `(id, organization_id)` foreign keys, so a row cannot claim one tenant and point at
  another's. RLS on every table compares `organization_id` with `app.current_organization_id()`.
- **Explicit grants (0006).** Browser roles get only what a migration grants: owner/admin write events
  (five columns) and modules_registry; any member updates `tasks.status`; everything else is read-only or
  hidden (attendees for owner/admin, `qr_uuid` for nobody; survey responses for owner/admin). `anon`
  gets nothing. Server writes go through `adminDb` after `requireOrgPermission`. Pinned by
  `tests/db/security-surface.test.ts` and `tests/db/access-hardening.test.ts`.
- **Proposals only.** The AI never writes domain rows. Every write goes through `proposals` →
  `applyProposal` (exactly once, all-or-nothing, "AI only overwrites what the AI last wrote" via
  `ai_fingerprint`; opened surveys and activated KPIs are never rewritten).
- **Relative due dates.** Tasks store `due_offset_days`; moving the event date re-flows the plan.
- **KPIs** come from the metric library in code (`src/lib/metrics/library.ts`), validated by the unit
  tests. Evidence is `UNREVIEWED`; `minSampleSize` values are unreviewed placeholders.
- **Surveys (0007).** DRAFT → OPEN creates a public link token; responses arrive anonymously through it,
  or are typed in by staff. Answers are validated against the stored questions of that version; the
  visitor profile (`q_is_local`, party size, days, nights, main reason, would-visit-anyway) and spend per
  category (kuruş) are stored for the engine. No respondent identity is stored, so no consent record is
  kept; sensitive questions need an explicit consent flag on the submission. Owner/admin can exclude a
  response with a reason.
- **Impact (0007).** Three levels (SPEND → ATTRIBUTABLE_SPEND → ECONOMIC_IMPACT). `src/lib/impact/engine.ts`
  runs the sufficiency gate and computes with the metric library's formulas; every coefficient
  (deadweight, displacement, leakage, multipliers) is an organization-recorded input with its source —
  none is in code. Economic impact also needs coefficients for every spend category with spend and the
  same price year for assumptions and multipliers. A run is stored immutably (trigger) with its checks,
  inputs and only the figures its level reached (CHECKs). Not yet: confidence intervals, weighting,
  inflation adjustment, report narratives. Open methodology questions: `docs/impact-open-decisions.md`.

## 3. AI contracts

| Stage | Draft schema (LLM) | Normalizer (deterministic) | Proposal |
|---|---|---|---|
| Core | `blueprintCoreDraftSchema` | `normalizeBlueprintCore`: city → plaka → NUTS-2, dates, modules from registry, objectives, stakeholder placeholders | `blueprint.core` |
| Registration | `registrationDraftSchema` | `normalizeRegistration`: tickets, form fields, KVKK consent, paid-ticket gate | not in the MVP (`unsupported`) |
| Tasks | `buildTasksDraftSchema(workstreams)` | `normalizeTasks`: keys, workstream enum, phase from offset, cycle breaking, due dates, coverage warnings | `blueprint.tasks` |
| KPIs | `buildKpisDraftSchema(candidates)` | `normalizeKpis`, `deriveDataRequirements`, `deriveMeasurementTasks` | `blueprint.kpis` (KPIs and measurement tasks) |
| Surveys | `buildSurveysDraftSchema(audiences)` | `normalizeSurveys`: bank questions first, AI extras, KVKK gate | `blueprint.surveys` |
| Budget & risks | `buildBudgetRisksDraftSchema(workstreams)` | `normalizeBudgetRisks`: no invented amounts, 1–5 risk grid, total-budget check | not in the MVP (`unsupported`) |

- **Provider-safe draft schemas.** Every key is required, unknowns are `null`, and there are no regex, length or numeric bounds. A test enforces this for all six.
- **Strict validation afterwards.** Strict schemas run only after normalization.
- **Determinism.** Temperature is 0, each stage has its own system prompt, and few-shot examples are typed. If a schema changes, the example breaks the build.

### Routes

| Route | Purpose |
|---|---|
| `POST /api/ai/blueprint` | Stage 1. Streams a preview to `useObject`; `after()` → `finalizeCoreGeneration` stores a PENDING `blueprint.core` proposal or records the failure. Nothing is applied from the stream. |
| `POST /api/proposals/:id` `{action: "apply" \| "reject", opIndexes?}` | Applies or rejects any proposal card. |
| `POST /api/ai/blueprint/sections` `{eventId, sections?}` | Stage 2. Returns 202; sections arrive as proposal cards (`GET /api/proposals`). Pass `sections: ["tasks"]` to regenerate a single section. |
| `POST /api/ai/event-builder` | Original single-shot event config. Single-shot event config (unchanged). |
